You can treat this as a “device–cloud offloading” and “expert routing” problem: the smartest logic combines cheap heuristics, learned predictors, and feedback from real usage. [requesty](https://www.requesty.ai/blog/the-future-of-llm-routing-on-device-edge-ai-and-federated-models-1751656903)

## 1. Decide what you’re optimizing

First define a scalar objective that trades off quality vs. latency vs. cost vs. privacy per request. For example: [arxiv](https://www.arxiv.org/abs/2210.05182)

- Utility = model_quality_score − α·latency − β·cloud_cost − γ·privacy_risk. [pmc.ncbi.nlm.nih](https://pmc.ncbi.nlm.nih.gov/articles/PMC12864935/)
- Different users/tenants can have different weights α, β, γ, and hard constraints (e.g., “never send PHI off-device”). [requesty](https://www.requesty.ai/blog/the-future-of-llm-routing-on-device-edge-ai-and-federated-models-1751656903)

Your routing algorithm should explicitly try to maximize this utility subject to constraints like “p95 latency < X ms” and “cloud budget per day < Y.” [ieeevtc](https://www.ieeevtc.org/vtc2023fall/DATA/2023002860.pdf)

## 2. A practical baseline router (what you’d ship first)

Start with a hybrid of rules and a small learned classifier; this gets you 80% of the benefit with low complexity. [arxiv](https://arxiv.org/html/2509.24050v3)

For each incoming request, compute:

- Request features: prompt length, language, domain, presence of PII markers, user priority; optionally simple embeddings or perplexity from a small encoder/SLM. [openreview](https://openreview.net/forum?id=SwHnok3JtD)
- Context features: on-device load, battery level (mobile), current network bandwidth/RTT, rolling latency and error stats for both local and cloud. [arxiv](https://www.arxiv.org/abs/2210.05182)
- Policy features: user tier (free vs. paid), privacy mode, budget remaining, SLA class. [pmc.ncbi.nlm.nih](https://pmc.ncbi.nlm.nih.gov/articles/PMC12864935/)

Routing policy (baseline):

1. Hard privacy/availability rules  
   - If request or user is marked “must stay local,” route to on-device regardless of other signals. [requesty](https://www.requesty.ai/blog/the-future-of-llm-routing-on-device-edge-ai-and-federated-models-1751656903)
   - If device is offline or network unstable beyond threshold, force local or a cached/fallback model. [arxiv](https://www.arxiv.org/abs/2210.05182)

2. Obvious-light vs obvious-heavy heuristics  
   - Very short, low-risk requests (simple Q&A, autocomplete, routing, keyword extraction) → local SLM. [requesty](https://www.requesty.ai/blog/the-future-of-llm-routing-on-device-edge-ai-and-federated-models-1751656903)
   - Very long, reasoning-heavy, or tool-heavy prompts (code, multi-step reasoning, large context) → cloud LLM if budget allows. [ieeevtc](https://www.ieeevtc.org/vtc2023fall/DATA/2023002860.pdf)

3. Learned classifier for ambiguous cases  
   - Train a small classifier (or even a SLM head) to predict “can local model answer this within quality threshold?” using offline labels generated by comparing local vs. cloud answers. [arxiv](https://arxiv.org/html/2509.24050v3)
   - If classifier predicts failure or low confidence for local, offload to cloud; otherwise run locally. [openreview](https://openreview.net/forum?id=SwHnok3JtD)

4. Budget- and latency-aware overrides  
   - If cloud spend is near budget or cloud latency is currently high, increase the threshold for offloading (i.e., become more conservative about using cloud). [pmc.ncbi.nlm.nih](https://pmc.ncbi.nlm.nih.gov/articles/PMC12864935/)
   - For high-priority users or latency-insensitive batch tasks, allow more liberal offloading. [ieeevtc](https://www.ieeevtc.org/vtc2023fall/DATA/2023002860.pdf)

This baseline is essentially a supervised offloading strategy, which has been shown to significantly cut latency while preserving accuracy in edge–cloud DNN setups. [arxiv](https://www.arxiv.org/abs/2210.05182)

## 3. More advanced routing: learning from feedback

Once you have logs of (request, routing decision, latency, cost, quality proxy), you can upgrade to learning-based routing. [arxiv](https://arxiv.org/html/2509.24050v3)

### 3.1 Supervised “difficulty” estimation

- Label historical prompts as “local sufficient” vs “needs cloud” by comparing human or automatic quality scores of local vs. cloud answers. [openreview](https://openreview.net/forum?id=SwHnok3JtD)
- Train:  
  - A separate classifier (e.g., gradient-boosted trees or a small transformer) on features above, or  
  - A small router model that reads the prompt and outputs a probability of “cloud needed.” [arxiv](https://arxiv.org/html/2501.09636v1)
- Use calibrated probabilities and thresholds tuned per segment (user tier, device class, region) to meet SLAs and budgets. [pmc.ncbi.nlm.nih](https://pmc.ncbi.nlm.nih.gov/articles/PMC12864935/)

This is analogous to the “external router classifier” used in collaborative device–cloud LLM frameworks. [arxiv](https://arxiv.org/html/2509.24050v3)

### 3.2 Context-aware RL or bandits

For highly dynamic environments (mobile networks, variable load), model routing as a contextual bandit / RL problem. [ieeevtc](https://www.ieeevtc.org/vtc2023fall/DATA/2023002860.pdf)

- State: current network conditions, device load, running budget, task type, user priority, recent quality metrics. [arxiv](https://www.arxiv.org/abs/2210.05182)
- Action: choose local vs. cloud (possibly which cloud model/tier). [pmc.ncbi.nlm.nih](https://pmc.ncbi.nlm.nih.gov/articles/PMC12864935/)
- Reward: the utility defined earlier (quality proxy − latency − cost − privacy penalty) plus penalties if SLAs are violated. [openreview](https://openreview.net/forum?id=SwHnok3JtD)

Approaches:

- Contextual bandit to adapt routing thresholds online with safe, gradual exploration. [ieeevtc](https://www.ieeevtc.org/vtc2023fall/DATA/2023002860.pdf)
- Deep RL (DQN/actor–critic) or active-inference-based decision-making for multi-objective optimization in multi-tier networks. [pmc.ncbi.nlm.nih](https://pmc.ncbi.nlm.nih.gov/articles/PMC12864935/)

Studies in intelligent edge computing and LLM offloading show RL-based schedulers adapt better than fixed thresholds when workloads and network conditions change. [ieeevtc](https://www.ieeevtc.org/vtc2023fall/DATA/2023002860.pdf)

### 3.3 Let the local LLM route itself

Recent work directly trains the on-device LLM to *decide when to call the cloud* as part of post-training. [arxiv](https://arxiv.org/html/2509.24050v3)

- The local model generates its answer and, if uncertain (as learned during training), emits a special “ask cloud” action instead of a final answer. [openreview](https://openreview.net/forum?id=SwHnok3JtD)
- Training casts this as a hierarchical reward maximization problem where correct local answers, appropriate offloads, and limited cloud usage are all encoded in the reward. [arxiv](https://arxiv.org/html/2509.24050v3)

This eliminates a separate router, makes routing depend on the model’s own reasoning trace, and has been shown to improve both routing quality and on-device competence. [openreview](https://openreview.net/forum?id=SwHnok3JtD)

## 4. Useful patterns from Mixture-of-Experts

Mixture-of-Experts (MoE) systems solve a similar routing problem across many experts; several tricks transfer well to device–cloud routing. [skywork](https://skywork.ai/blog/mixture-of-experts-moe-llms-architecture-routing-gemini/)

- Capacity constraints: treat cloud as having limited “capacity” per time window (budget, rate limits) and enforce capacity factors so the router does not overload it. [cameronrwolfe.substack](https://cameronrwolfe.substack.com/p/moe-llms)
- Load balancing: penalize policies that overuse cloud when the local model could handle requests, or vice versa, analogous to auxiliary balancing losses in MoE. [skywork](https://skywork.ai/blog/mixture-of-experts-moe-llms-architecture-routing-gemini/)
- Stability: regularize router outputs so small input changes do not flip decisions unpredictably, inspired by “z-loss” and other router-stabilizing techniques. [cameronrwolfe.substack](https://cameronrwolfe.substack.com/p/moe-llms)

Conceptually, you can think of “local SLM” and “cloud LLM” as two experts, with the router learning to pick a sparse subset under capacity and cost constraints. [arxiv](https://arxiv.org/html/2501.09636v1)

## 5. Concrete architecture and data you need

A production-ready setup usually looks like this. [requesty](https://www.requesty.ai/blog/the-future-of-llm-routing-on-device-edge-ai-and-federated-models-1751656903)

- On-device:  
  - A small, fast SLM for most interactions and to produce cheap features (e.g., difficulty estimates, embeddings).  
  - A light router module or head attached to the SLM for real-time routing decisions. [requesty](https://www.requesty.ai/blog/the-future-of-llm-routing-on-device-edge-ai-and-federated-models-1751656903)

- Cloud:  
  - One or more high-capability models (different sizes/tiered pricing).  
  - Central policy service that tracks budget, per-user quotas, global latency stats, and updates routing thresholds/policies pushed to devices. [requesty](https://www.requesty.ai/blog/the-future-of-llm-routing-on-device-edge-ai-and-federated-models-1751656903)

- Logging & training loop:  
  - For a sample of requests, run both local and cloud to get labels for “who did better.” [arxiv](https://www.arxiv.org/abs/2210.05182)
  - Collect latency, errors, user feedback, cost; retrain the classifier/RL router regularly and ship updated policies. [arxiv](https://www.arxiv.org/abs/2210.05182)

### Example flow

1. Device receives a prompt, computes features and a difficulty score via the local SLM/router head.  
2. Router consults local rules plus its learned policy, adjusted by current budget/latency parameters from the central policy service.  
3. It routes to local or cloud, possibly with a small exploration probability in low-risk contexts to keep learning signals fresh. [pmc.ncbi.nlm.nih](https://pmc.ncbi.nlm.nih.gov/articles/PMC12864935/)
4. Logs used offline to refine routing thresholds, train better classifiers, or update RL policies. [ieeevtc](https://www.ieeevtc.org/vtc2023fall/DATA/2023002860.pdf)
